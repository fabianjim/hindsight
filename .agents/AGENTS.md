# Hindsight — Agent Guide

Hindsight is the Python AI service behind Vestry, a portfolio journal for reflective investors. Vestry's Java backend is the system of record and the only public API; hindsight is called only by that backend and is never publicly reachable. Vestry must stay fully functional when hindsight is off or down. The AI helps users reflect on their own decisions (what they thought, did, and what happened). It never predicts prices or gives buy/sell advice.

## Working rules

- Explore the affected code and tests before changing anything. When this guide and the code disagree, trust the code, report it, and fix this guide if it was stale.
- Work in small steps. State the next step (files, commands) and wait for approval before creating files or adding dependencies. 
- Ask first for scope expansion, product decisions, spending, publishing, deployment, and changes to the shared database outside the `ai` schema.
- Paid LLM calls (live evals, real-model runs) need explicit approval for each run. Tests use fakes.
- Update this file only when you learn something significant for future agents. Don't log task history here.

## Layout and commands

- `src/hindsight/`: `main.py` (app, `/health`, the `/v1` router), `api.py` (`/v1` routes), `wire.py` (`WireModel`, camelCase JSON), `config.py` (settings from `HINDSIGHT_*` env vars or `.env`), `auth.py` (service token), `db.py` (async SQLAlchemy + psycopg), `models.py` (declarative base, `ai` schema), `budget.py` (AI spend ledger), `spend.py` (`BudgetMiddleware`), `pricing.py` (per-model prices), `citations.py` (quote checks), `enrichment.py` (entry insight extraction; prompt in `prompts/`), `insights.py` (`InsightStore` for `ai.entry_insights`), `reflection_aids.py` (`ReflectionAidStore` for `ai.reflection_aids`: one aid per user, entry and New York day, `DAILY_AIDS` per user per day), `reflection.py` (`ReflectionAidGenerator`: a cited recap of later entries plus questions for Reflect with AI; prompt in `prompts/`), `pipeline.py` (`EntrySource` and `process_entry`: read, skip if unchanged, extract, re-check, save), `worker.py` (pgmq consumer, run with `python -m hindsight.worker`), `sweep.py` (`Sweeper`: queues entries without a current insight, removes orphans), `vocab.py` (shared enums), `llm.py` (LangChain model factory, `UserContext`), `tracing.py` (Langfuse).
- `migrations/`: Alembic, configured in `pyproject.toml` (no `alembic.ini`).
- `contract/openapi.json`: the API contract vestry consumes, generated by `scripts/export_openapi.py`.
- `evals/entry_insight.jsonl`: synthetic labeled entries (never real user data), scored by `hindsight.evals` and run by `scripts/eval_entry_insight.py`.
- `evals/reflection_aid.jsonl`: synthetic cases for Reflect with AI, scored by `hindsight.reflection_evals` (presence, quote survival, no numbers, no advice, feelings only when the writer named them) and run by `scripts/eval_reflection_aid.py`, which prints every answer because scores can't show tone.
- `tests/`: pytest. DB tests need `docker compose up -d`; the `database_url` fixture recreates a `hindsight_test` database and migrates it. The `settings_env` fixture blanks the API and Langfuse keys, so a real `.env` never reaches tests. `tests/fakes.py` has `FakeToolModel`, a scripted chat model that can call tools.
- Stack: Python 3.13, uv, FastAPI, LangChain 1.x (`create_agent`, middleware; never `langchain-classic`, `LLMChain` or `AgentExecutor`), SQLAlchemy 2 + psycopg 3, Alembic, Langfuse v5, ruff, pyright (strict), pytest.
- Commands:
  - `uv run fastapi dev` (needs `.env` from `.env.example`)
  - `docker compose up -d` (local `supabase/postgres` on port 54322, same version as prod)
  - `uv run alembic upgrade head`, `uv run alembic revision --autogenerate -m "..."`
  - `uv run pytest`, `uv run ruff check .`, `uv run ruff format .`, `uv run pyright`
  - `uv run python -m scripts.export_openapi` after any route change
  - `uv run python -m hindsight.worker` (the queue consumer; needs the API key and vestry's `core_read` view)
  - `uv run python -m scripts.eval_entry_insight` (dry run, free); add `--paid` to call the real model, which needs explicit approval for each run. `scripts.eval_reflection_aid` works the same way. With Langfuse keys it records an experiment run; without them it prints scores.
- CI (`.github/workflows/ci.yml`): lint, format, typecheck, tests; migrations applied to a real Postgres plus `alembic check`; Docker build. Actions are pinned to commit SHAs.
- Deploy: on main, after those jobs pass, CI pushes the arm64 image to ECR and runs vestry's `deploy/deploy.sh`, which deploys the newest vestry and hindsight images together to the EB environment `vestry-api-env`. Production migrations are manual: run `alembic upgrade head` as `postgres` before pushing code that needs them (migrations stay additive, so old code keeps working). The runtime login is `hindsight`, with the grants in `scripts/runtime_role.sql`.

## Invariants (high-risk; verify carefully when touched)

**Access**
- Every `/v1` route requires vestry's service token (`require_service_token`, constant-time compare). Only `/health` is open.
- Hindsight trusts the `user_id` vestry sends. Tools get the user from `runtime.context` (`UserContext`), never from a tool argument the model can fill. `tests/test_llm.py` guards this pattern.

**Data**
- Hindsight writes only to the `ai` schema. Alembic's `include_name` filter ignores every other schema; without it, autogenerate proposes dropping vestry's tables.
- Vestry's tables are managed by Hibernate (`ddl-auto=update`). Read vestry data only through vestry-owned `core_read` views, never raw tables. The agreed view is `core_read.journal_entries(id, user_id, entry_type, body, ticker, timestamp, price_snapshot, tags text[])`; changing it is a contract change in both repos. Tests stand in for it with a same-shaped table (`tests/conftest.py`).
- Queue messages (`pgmq` queue `entry_events`, created by hindsight's migration) are `{"entryId": n}`: IDs only, never entry text. The worker deletes a message once it's handled, archives it (the dead-letter queue) after 5 reads or if it's malformed, and checks the budget before reading so a spent budget doesn't use up read counts. Worker logs carry IDs and exception class names only.
- The sweep is the guarantee; the queue is only the fast path. pg_cron (job `hindsight-entry-sweep`, hourly at :17) sends `{"sweep": "entries"}` to the same queue. pg_cron installs only in the `cron.database_name` database, so the migration skips it elsewhere (including `hindsight_test`) and CI checks the job exists. The sweep applies `process_entry`'s rules in bulk and never calls the model. It won't delete orphaned insights when more than 10% (floor 50) look orphaned, because that usually means a broken or empty view on vestry's side. The pipeline always reads the entry's current state and re-reads it before saving, so stale or out-of-order events can't overwrite newer text.
- Demo visitors' data lives in vestry's memory and arrives in the request body. Never persist it.
- Demo visitors never cause a model call. Vestry shows them saved aids for the demo template account through the read-only `GET /v1/users/{userId}/reflection-aids`; only vestry's nightly demo job generates them, through the normal POST and its daily limit.
- Rows keyed by vestry IDs (e.g. `ai.entry_insights.entry_id`) have no foreign keys, since vestry owns those tables. Every read is scoped by `user_id` as well as the ID.

**Contract**
- `contract/openapi.json` must match the code (`tests/test_contract.py`). Operation IDs are route function names, so they become Java method names.
- Contract changes must be backward compatible. Hindsight and vestry deploy independently, in any order.
- Models vestry sees extend `WireModel`: camelCase on the wire, snake_case in Python and in stored `jsonb`, and both are accepted on input. Model-facing schemas like `Extraction` stay plain `BaseModel`, because the prompt names their fields.

**Tracing**
- Langfuse redacts all inputs, outputs and metadata unless code runs inside `capture_content()`, which is only for demo and eval runs.
- Without both Langfuse keys, no client or callback is created.

**Spend**
- Every model call reserves its worst-case cost in `BudgetLedger` before it runs and settles the real cost after. A settlement over the reservation blocks all spending until someone resets `ai.budget.blocked`. Crashed or unsettled work keeps its full reservation.
- Each version of an entry's text gets at most `POISON_AFTER` (3) failed paid attempts, tracked in `ai.entry_failures` by `input_hash`; after that it's a poison entry and `process_entry` returns `POISONED` without calling the model. Budget refusals, `TRANSIENT_ERRORS` (provider outages, rate limits, timeouts, database connection errors) and errors before the model call never count, so an outage can't poison healthy entries. New text, prompt or model means a new hash and fresh attempts. `TRANSIENT_ERRORS` names OpenAI's exception classes, so update it when switching providers.
- Every agent gets `BudgetMiddleware`, listed last so it wraps the model directly and each retry reserves again. It caps `max_tokens`, reads the job from `runtime.context.generation_id`, and only implements the async hook, so a sync `invoke` raises instead of skipping the budget.
- `get_chat_model()` matches vestry's provider settings: no SDK retries (each would be an unreserved charge), 5 s connect / 30 s read timeouts, `store=False`, and only `HINDSIGHT_OPENAI_API_KEY`, never a stray `OPENAI_API_KEY`. The OpenAI SDK (3.x) runs on `httpx2`, not `httpx`: use `openai.Timeout` and the SDK's exception classes, never httpx ones.
- Enrichment reserves a fixed `ALLOWANCE_MICROS`; reflection aids reserve per request (`allowance_for`), sized from the rendered message, because their input varies with the number of later entries. `test_reservation_covers_the_largest_possible_request` guards that bound.
- `pricing.PRICES` holds pinned model snapshots only. Changing `HINDSIGHT_CHAT_MODEL` means adding its price; unknown models are refused.

**AI output**
- Numbers (returns, P/L, patterns) are computed deterministically. The LLM extracts, narrates and connects, and must cite entry IDs that the server validates.
- Every AI claim carries `Citation`s (entry ID plus a quote). `citations.verified` keeps only quotes found in the cited entry; a claim left with none is dropped, never stored.
- Structured output uses `ProviderStrategy(..., strict=True)`. LangChain's default sends `strict: false`, so OpenAI wouldn't enforce the schema. Strict mode rejects any object without `additionalProperties: false`, so every model-facing model sets `extra="forbid"`.
- `input_hash` covers the prompt text, the model and the rendered entry, so editing a prompt re-enriches everything. Bump `PROMPT_VERSION` with it.
